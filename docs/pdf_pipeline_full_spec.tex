\section{Executive Summary}

SCI-OCR is a local-first document processing pipeline that receives a PDF and
produces an ordered Markdown article, together with a complete set of
intermediate artifacts for inspection and debugging.

The current implemented pipeline is:

\begin{lstlisting}
Input PDF
  -> Page Rendering
  -> Layout
  -> Layout Assets and Routing
  -> OCR + optional Vision
  -> Assembly
  -> output/article.md
\end{lstlisting}

The system is no longer only a placeholder scaffold. It has a working FastAPI
orchestrator, stable Pydantic service contracts, a real CPU PP-DocLayoutV3
layout service, a real GLM-OCR worker, an optional llama-server-backed vision
adapter, deterministic assembly, representative PDF fixtures, and a job report
script.

\docnote{The core engineering principle remains unchanged: model backends must
be replaceable without changing downstream artifact contracts.}

\section{Current Capabilities}

The current repository supports:

\begin{itemize}[leftmargin=1.2cm]
\item FastAPI orchestrator with \texttt{GET /health} and \texttt{POST /run}.
\item Input file validation and unique job creation.
\item Persistent job workspace under \texttt{jobs/output/<job\_id>/}.
\item \texttt{meta.json}, \texttt{trace.json}, and \texttt{logs.jsonl}.
\item PDF page rendering to PNG at 300 DPI by default, with optional 400 DPI.
\item HTTP layout service calls for rendered pages.
\item Layout stub service for fast contract tests.
\item CPU PP-DocLayoutV3 service preserving native labels as
  \texttt{layout\_label}.
\item Raw and normalized layout artifacts.
\item Layout overlays and block crops for every detected layout block.
\item Deterministic routing from layout labels to OCR or vision.
\item Shared OCR contract and OCR stub.
\item GLM-OCR worker behind the same OCR contract.
\item Optional vision contract and \texttt{vision\_llama} adapter.
\item Pending vision manifest when the vision backend is unavailable.
\item Deterministic assembly into \texttt{debug/content\_stream.json} and
  \texttt{output/article.md}.
\item Representative fixtures for text, tables, formulas, images, bar charts,
  and line charts.
\item \texttt{scripts/report\_job.py} for manual validation of persisted job
  artifacts.
\item Tests covering contracts, routing, assembly, fixtures, service stubs, and
  selected integrations.
\end{itemize}

\section{Pipeline Flow}

\subsection{API Request}

The orchestrator exposes:

\begin{lstlisting}
GET /health
POST /run
\end{lstlisting}

The \texttt{/run} request body is:

\begin{lstlisting}
{
  "input_path": "C:/input/test.pdf",
  "dpi": 300
}
\end{lstlisting}

\texttt{dpi} is optional and can be 300 or 400.

\subsection{Execution Order}

\begin{lstlisting}
validate input
  -> create job_id
  -> create job folders
  -> copy original file
  -> write metadata, trace, log
  -> render PDF pages
  -> call layout service
  -> write raw and normalized layout artifacts
  -> create overlays and crops
  -> route crops to OCR or vision
  -> start and poll async OCR jobs for text/table/formula crops
  -> call optional vision service for image/chart crops
  -> write pending vision manifest if needed
  -> build content_stream.json
  -> render output/article.md
\end{lstlisting}

\section{Job Artifact Contract}

Every run creates:

\begin{lstlisting}
jobs/output/<job_id>/
+-- original/
+-- preprocessed/
+-- assets/
|   +-- pages/
|   +-- crops/
|   +-- layout/
+-- debug/

|   +-- layout_raw_page_0001.json
|   +-- layout_normalized_page_0001.json
|   +-- layout_assets.json
|   +-- ocr_manifest.json
|   +-- ocr_raw_page_0001.json
|   +-- ocr_normalized_page_0001.json
|   +-- vision_manifest.json
|   +-- vision_raw_page_0001.json
|   +-- vision_normalized_page_0001.json
|   +-- vision_pending_manifest.json
|   +-- content_stream.json
|   +-- assembly_manifest.json
+-- output/
|   +-- article.md
+-- meta.json
+-- trace.json
+-- logs.jsonl
\end{lstlisting}

\subsection{Artifact Meaning}

\begin{itemize}[leftmargin=1.2cm]
\item \texttt{original/}: unchanged input file.
\item \texttt{assets/pages/}: rendered page PNG files.
\item \texttt{assets/layout/}: human-readable layout overlays.
\item \texttt{assets/crops/}: crops for every layout block.
\item \texttt{debug/}: normalized and raw stage artifacts.
\item \texttt{output/article.md}: final LLM-ready article representation.
\item \texttt{meta.json}: high-level job and stage summary.
\item \texttt{trace.json}: ordered event timeline.
\item \texttt{logs.jsonl}: append-only structured logs.
\end{itemize}

\section{Layout Service}

\subsection{Role}

Layout is an external persistent HTTP service. It receives one rendered page
image and returns structured layout blocks. The layout service owns detection
and block typing. It does not run OCR, generate crops, or assemble Markdown.

Current layout implementations:

\begin{itemize}[leftmargin=1.2cm]
\item \texttt{services/layout\_stub}: fast deterministic stub.
\item \texttt{services/layout\_ppdoclayoutv3\_cpu}: CPU PP-DocLayoutV3 backend.
\end{itemize}

\subsection{Endpoints}

\begin{lstlisting}
GET  /health
GET  /ready
POST /layout
\end{lstlisting}

\subsection{Normalized Layout}

The service response is persisted as raw output, then normalized into a stable
format used by downstream stages:

\begin{lstlisting}
{
  "stage": "layout",
  "status": "completed",
  "source": "PP-DocLayoutV3",
  "job_id": "job-0001",
  "page_number": 1,
  "image": {
    "path": ".../assets/pages/page_0001.png",
    "width": 2480,
    "height": 3508
  },
  "blocks": [
    {
      "block_id": "p1_b1",
      "type": "text",
      "layout_label": "content",
      "bbox": [100, 100, 700, 180],
      "confidence": 0.98,
      "order": 1,
      "source": "PP-DocLayoutV3"
    }
  ],
  "warnings": []
}
\end{lstlisting}

\section{Block Routing}

Routing is deterministic and model-free. It maps layout labels to downstream
services, recognition tasks, requested output formats, and assembly roles.

\begin{lstlisting}
text-like blocks -> OCR    -> markdown
table blocks     -> OCR    -> markdown
formula blocks   -> OCR    -> latex
image/chart      -> Vision -> markdown or pending placeholder
\end{lstlisting}

Native PP-DocLayoutV3 labels are preferred when available because they preserve
more semantic detail than canonical block types.

\subsection{Important Label Families}

\begin{longtable}{p{4cm}p{3cm}p{3cm}p{3cm}}
\toprule
Label family & Target & Task & Format \\
\midrule
Text-like labels & OCR & text & markdown \\
Table & OCR & table & markdown \\
Display/inline formulas & OCR & formula & latex \\
Image labels & Vision & image & none \\
Chart labels & Vision & chart & none \\
\bottomrule
\end{longtable}

Images and charts are intentionally not sent to OCR. They require visual
description, chart extraction, diagram reconstruction, or placeholder handling.

\section{OCR Service}

\subsection{Role}

OCR is an external persistent worker service. It receives one cropped block
image and returns recognized content in the format requested by the
orchestrator.

Current OCR implementations:

\begin{itemize}[leftmargin=1.2cm]
\item \texttt{services/ocr\_stub}: deterministic contract-compatible stub.
\item \texttt{services/ocr\_glm}: real GLM-OCR worker.
\end{itemize}

Docker Compose points OCR traffic at \texttt{ocr\_glm} by default.

\subsection{Endpoints}

\begin{lstlisting}
GET  /health
GET  /ready
POST /ocr
POST /ocr/jobs
GET  /ocr/jobs/{task_id}
\end{lstlisting}

The synchronous \texttt{POST /ocr} endpoint remains available for compatibility
and fast tests. Docker Compose enables async OCR by default. In that mode the
orchestrator starts a job, polls status, and only considers the job stalled when
\texttt{last\_heartbeat\_at} stops updating beyond the configured stall
timeout.

The first async implementation keeps GLM-OCR generation as one blocking
\texttt{model.generate(...)} call. A background heartbeat ticker updates the
job while generation runs. Token-level progress and partial output streaming
are not implemented yet.

\subsection{GLM-OCR Prompt Mapping}

\begin{lstlisting}
text    -> Text Recognition:
table   -> Table Recognition:
formula -> Formula Recognition:
\end{lstlisting}

Formula responses are normalized by removing outer display wrappers such as
\texttt{\$\$...\$\$}. Assembly owns final Markdown wrapping.

\section{Vision Service}

\subsection{Role}

Vision is optional. It receives image/chart/figure crops and returns
Markdown-ready visual content. If the service is not configured, unavailable,
or times out, the pipeline writes a pending vision manifest and continues:

\begin{lstlisting}
debug/vision_pending_manifest.json
\end{lstlisting}

Current implementation:

\begin{itemize}[leftmargin=1.2cm]
\item \texttt{services/vision\_llama}: adapter around an external multimodal
  \texttt{llama-server}.
\end{itemize}

\subsection{Runtime Split}

\begin{lstlisting}
Windows host:
  llama-server on http://127.0.0.1:8080

Docker:
  vision_llama service on http://vision_llama:8000
  calls http://host.docker.internal:8080
\end{lstlisting}

\subsection{Vision Output}

The adapter asks the model to classify a visual crop as:

\begin{lstlisting}
photo_or_illustration
chart_or_plot
diagram_or_flowchart
table_like_visual
unknown
\end{lstlisting}

It returns Markdown for descriptions, charts, approximate data tables, or
Mermaid diagrams when possible.

\section{Assembly}

Assembly is currently an orchestrator module rather than a separate worker. It
does not perform model inference. It reads normalized layout, OCR, vision, and
pending vision artifacts.

It produces:

\begin{lstlisting}
debug/content_stream.json
debug/assembly_manifest.json
output/article.md
\end{lstlisting}

The current ordering rule is:

\begin{lstlisting}
page_number -> order -> bbox top -> bbox left -> block_id
\end{lstlisting}

Rendering behavior:

\begin{itemize}[leftmargin=1.2cm]
\item titles become Markdown \texttt{\#} headings.
\item headings become Markdown \texttt{\#\#} headings.
\item text remains Markdown paragraphs.
\item tables are inserted as Markdown or HTML returned by OCR.
\item formulas are wrapped as display or inline LaTeX.
\item completed visual blocks insert vision Markdown.
\item pending visual blocks become blockquote placeholders.
\end{itemize}

\section{Docker Compose Runtime}

Docker Compose currently includes:

\begin{itemize}[leftmargin=1.2cm]
\item \texttt{orchestrator}
\item \texttt{layout\_stub}
\item \texttt{layout\_ppdoclayoutv3\_cpu}
\item \texttt{ocr\_stub}
\item \texttt{ocr\_glm}
\item \texttt{vision\_llama}
\item \texttt{assembly\_stub}
\end{itemize}

The default real pipeline path is:

\begin{lstlisting}
orchestrator
  -> layout_ppdoclayoutv3_cpu
  -> ocr_glm
  -> vision_llama, if external llama-server is ready
\end{lstlisting}

Important timeouts:

\begin{lstlisting}
LAYOUT_TIMEOUT_SECONDS=120
OCR_TIMEOUT_SECONDS=600
OCR_ASYNC_ENABLED=true
OCR_JOB_HTTP_TIMEOUT_SECONDS=30
OCR_JOB_POLL_INTERVAL_SECONDS=5
OCR_JOB_STALL_TIMEOUT_SECONDS=600
OCR_JOB_MAX_RUNTIME_SECONDS=0
VISION_TIMEOUT_SECONDS=1200
\end{lstlisting}

The OCR image installs CPU PyTorch wheels explicitly:

\begin{lstlisting}
torch==2.9.1+cpu
torchvision==0.24.1+cpu
\end{lstlisting}

\section{CPU Layout Scaling Notes}

PP-DocLayoutV3 through PaddleOCR/Paddle already uses internal CPU
parallelism. Current installed defaults are:

\begin{lstlisting}
DEFAULT_ENABLE_MKLDNN = True
DEFAULT_CPU_THREADS = 10
DEFAULT_MKLDNN_CACHE_CAPACITY = 10
\end{lstlisting}

Local measurements:

\begin{lstlisting}
1 unrestricted layout worker:
  about 5.3 seconds per page

3 separate layout containers limited to 2 CPU each:
  about 18.8 seconds per page on average
\end{lstlisting}

The second setup was slower because each worker was starved. One Paddle
inference process wants roughly 8-10 CPU threads.

Memory estimate:

\begin{lstlisting}
observed warmed worker peak: about 668 MiB
planning estimate: about 1.0 GiB
conservative budget: about 1.2 GiB per worker
\end{lstlisting}

Future high-core machines should scale layout with a worker pool:

\begin{lstlisting}
worker_count = floor(usable_cpu_cores / 10)
also cap by available_memory_gb / 1.2
\end{lstlisting}

Example sizing:

\begin{lstlisting}
8 cores   -> 1 worker
10 cores  -> 1 worker
15 cores  -> 1 worker
20 cores  -> 2 workers
32 cores  -> 3 workers
64 cores  -> 6 workers
400 cores -> about 40 workers, if memory and I/O allow it
\end{lstlisting}

This is a future development direction, not current implementation. The
detailed planning note lives in \texttt{docs/LAYOUT\_SCALING.md}.

\section{Current Limitations}

\begin{itemize}[leftmargin=1.2cm]
\item PP-DocLayoutV3 is wired as a CPU-only service and still needs broader
  quality validation on representative documents.
\item GLM-OCR CPU inference is slow because crops are processed one at a time;
  async OCR avoids one long HTTP request but does not speed up inference.
\item \texttt{vision\_llama} depends on an external multimodal
  \texttt{llama-server}; on CPU-class hardware it can be slow.
\item Chart extraction from vision output is approximate.
\item Assembly does not yet repair multi-column reading order, merge broken
  paragraphs, or associate captions with figures/charts beyond deterministic
  layout order.
\item There is not yet a GPU PP-DocLayoutV3 container.
\item There is not yet a quality validation harness with expected semantic
  assertions for representative jobs.
\end{itemize}

\section{Roadmap}

\subsection{Near Term}

\begin{itemize}[leftmargin=1.2cm]
\item Add a quality validation harness for representative job artifacts.
\item Validate CPU PP-DocLayoutV3 output quality on real and synthetic PDFs.
\item Validate GLM-OCR output quality on text, table, and formula crops.
\item Validate \texttt{vision\_llama} output on images, charts, and diagrams.
\item Improve vision prompts and normalization for chart data and Mermaid.
\item Add token-level OCR progress or partial output streaming if the runtime
  supports it cleanly.
\end{itemize}

\subsection{Performance}

\begin{itemize}[leftmargin=1.2cm]
\item Improve OCR throughput with batching, crop parallelism, or GPU execution.
\item Add future layout worker-pool support for high-core machines.
\item Keep one-worker \texttt{LAYOUT\_SERVICE\_URL} mode for ordinary desktops.
\item Consider \texttt{LAYOUT\_SERVICE\_URLS} for multi-worker page distribution.
\end{itemize}

\subsection{Backends}

\begin{itemize}[leftmargin=1.2cm]
\item Add a separate GPU PP-DocLayoutV3 service/container.
\item Replace or augment \texttt{vision\_llama} with specialized image, chart,
  and diagram processors when quality requirements are clearer.
\item Keep all replacements behind stable shared contracts.
\end{itemize}

\subsection{Assembly Quality}

\begin{itemize}[leftmargin=1.2cm]
\item Improve multi-column reading order.
\item Merge paragraphs split across layout blocks.
\item Associate captions with figures and charts.
\item Optionally filter headers, footers, and page numbers.
\end{itemize}

\section{Final Summary}

SCI-OCR is now best understood as an artifact-driven, replaceable-backend
pipeline:

\begin{lstlisting}
FastAPI orchestrator
  + stable shared contracts
  + PP-DocLayoutV3 CPU layout
  + GLM-OCR CPU OCR
  + optional llama-server vision
  + deterministic assembly
  + persistent artifacts for every stage
\end{lstlisting}

The next important engineering move is not another placeholder service. It is
quality measurement: build validation around representative PDFs so layout,
OCR, vision, and assembly improvements can be judged with repeatable evidence.
